Архитектура и модель данных

Разделение ответственности

Часть проекта Ответственность
django_project_borisuk/settings.py Приложения, PostgreSQL, шаблонизаторы, авторизация
django_project_borisuk/urls.py Общие маршруты, вход, выход, admin и подключение приложений
conferences/models.py Конференции, тематики, выступления и отзывы
conferences/forms.py Разрешённые пользователю поля ввода
conferences/views.py Проверка прав, обработка запросов, выборка данных
conferences/admin.py Административные формы и списки
project_first_app/ Учебные модели и интерфейсы практик 2.1–2.3
jinja2/ Общий макет и HTML-страницы
static/style.css Оформление без внешних библиотек

Django использует MVT, вариант архитектуры MVC. Модель описывает данные, представление выполняет обработку запроса, шаблон формирует HTML. Разделение позволяет проверять бизнес-правила независимо от оформления.

Связи сущностей

Источник Связь Получатель Смысл
Conference Многие ко многим Topic У конференции несколько тематик, тематика используется повторно
Registration Многие к одному Conference У конференции несколько выступлений
Registration Многие к одному User Пользователь выступает на разных конференциях
Review Многие к одному Conference Конференция имеет несколько отзывов
Review Многие к одному User Отзыв связан с автором
Car Многие ко многим через Ownership User История владельцев с собственными датами
DriverLicense Многие к одному User Удостоверение принадлежит пользователю

Ссылки на пользователя задаются через settings.AUTH_USER_MODEL. Это важно, поскольку здесь используется собственная модель User, а не встроенная auth.User.

Topic и Conference

Topic хранит уникальное название тематики. Conference содержит:

Поле Тип Назначение
title CharField(200) Название конференции
topics ManyToManyField Набор тематик
location CharField(200) Место проведения
start_date, end_date DateField Период
description TextField Описание мероприятия
venue_description TextField Описание площадки
participation_terms TextField Условия участия

Окончание не может быть раньше начала. Правило проверяется clean модели и ограничением conference_date_order в PostgreSQL. Конференции упорядочены по начальной дате и первичному ключу: такой порядок стабилен для пагинации.

Registration

Регистрация связывает текущего пользователя с конференцией и хранит тему выступления, аннотацию и результат. Пара conference/author уникальна: один пользователь имеет одну регистрацию на одну конференцию.

Значение в БД Отображение
pending Не рассмотрено
recommended Рекомендовано к публикации
rejected Не рекомендовано к публикации

Список значений задан TextChoices и ограничением БД. Пользовательская форма принимает только presentation_title и abstract. author, conference и result не входят в разрешённые поля автора.

После редактирования темы или аннотации результат сбрасывается в pending: администратор рассматривал другое содержание. Сохранение без изменений результат не сбрасывает. Удаление регистрации не удаляет пользователя и саму конференцию.

Review

Отзыв содержит конференцию, автора, текст, рейтинг и две даты конференции. Автор и даты назначаются сервером. Пользователь не передаёт их как доверенные поля формы.

Даты сохраняются отдельными значениями, а не вычисляются каждый раз из текущей карточки: если организатор перенесёт конференцию, уже написанный отзыв сохранит исходный контекст. Рейтинг ограничен 1–10 в HTML-поле, валидаторах и PostgreSQL. Пустой текст отвергается формой.

Условие не требует проверять фактическое посещение конференции или ждать её окончания перед отзывом, поэтому таких дополнительных ограничений нет.

Удаление связанных записей

Предметные ForeignKey используют CASCADE. Удаление конференции удаляет её регистрации и отзывы, удаление пользователя — связанные с ним записи. Привязки тематики удаляются вместе с соответствующей связью M2M; удаление одной конференции не удаляет саму общую тематику.

Удаление конференций выполняется через Django-admin с его стандартным подтверждением и правами. В пользовательском интерфейсе доступно удаление только собственной регистрации.

Модель практик

Учебные сущности отделены от конференций в project_first_app. Общим остаётся User, наследующий AbstractUser. Дополнительные поля — дата рождения, паспорт, адрес и национальность. Для автора конференции без автомобиля они необязательны.

Для автовладельца все шесть полей, включая имя и фамилию, проверяются validate_owner_fields. Эта проверка вызывается:

  1. При вводе владельца через OwnerForm.
  2. При создании или изменении Ownership и DriverLicense через их clean.
  3. При редактировании пользователя с паспортом или существующими связями владения/удостоверений.

Таким образом, нельзя сначала создать пустого автора, назначить ему автомобиль через admin, а затем удалить обязательные сведения. Межтабличные проверки выполняются моделями и admin-формами. Они не объявляются PostgreSQL-триггерами: при собственных операциях ORM требуется вызвать full_clean перед save.

Ownership дополнительно проверяет порядок и пересечения дат одного автомобиля. Проверка рассчитана на последовательные учебные операции, не на конкурентные записи из нескольких независимых процессов.
