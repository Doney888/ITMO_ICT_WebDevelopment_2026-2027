Тестирование и подготовка к защите

Воспроизводимая проверка

Все команды выполняются из laboratory_work_2 с активным Python-окружением и настроенным подключением к отдельной учебной PostgreSQL:

python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate --check
python manage.py test --verbosity 2
python -m compileall -q django_project_borisuk conferences project_first_app
ruff check .
ruff format --check .
python -m mkdocs build --strict
git diff --check

Тестовый runner создаёт test_web_lab2, применяет все миграции, выполняет проверки и удаляет временную базу. Учебная web_lab2 с демонстрационными данными не является хранилищем тестовых записей. Роль PostgreSQL должна иметь право CREATEDB.

Состав автоматических тестов

Всего выполнены 44 теста: 26 в conferences и 18 в project_first_app. Они проверяют наблюдаемое поведение через HTTP-клиент Django и ограничения БД.

Группа Что проверяется
Регистрация и сессия Создание пользователя, хеш пароля, запрет назначения себе роли, вход и POST-выход
Доступ гостя Просмотр страниц и запрет записи без входа
Выступления Создание, повтор, пустая форма, изменение, удаление, запрет чужих записей
Результаты Сброс после изменения текста, сохранение без изменений, права администратора и admin-форма
Отзывы Назначение автора и дат, границы рейтинга, отклонение неверных значений, HTML-экранирование
Каталог Поиск, совместный фильтр, пагинация, пустая выборка и ошибочный номер страницы
Идентификаторы 5000 цифр, выход за bigint, не-ASCII цифры, ноль, отрицательное и нечисловое значение
CSRF POST без токена запрещён; форма с корректным токеном работает
Практики Создание владельцев и автомобилей через FBV/CBV, карточки, редактирование и удаление
Admin практик Два владельца, четыре автомобиля и шесть владений через POST-формы
Модель владельца Обязательная дата, отсутствие неполного владельца, запрет очистки полей и переназначения
Связи M2M через Ownership, удостоверение, порядок и пересечения дат
Повторяемость Повторный seed_demo не создаёт дубли своего набора данных

У TestCase тестовые данные изолированы транзакциями. В проверках PostgreSQL IntegrityError ожидается внутри transaction.atomic, чтобы ошибка ограничения не оставляла транзакцию теста в непригодном состоянии.

Обычный тестовый клиент не требует CSRF, поэтому отдельная проверка использует Client(enforce_csrf_checks=True). Это позволяет проверить реальную обязательность токена, а не только наличие HTML-поля.

Проверка прав вручную

Используйте две разные учётные записи — обычного автора и администратора.

Действие Ожидаемый результат
Гость открывает каталог и карточку Данные видны
Гость пытается написать отзыв Перенаправление на вход
Автор регистрирует выступление Запись видна в его карточке
Другой автор открывает изменение этого выступления 404
Обычный автор открывает /participants/ 403
Администратор открывает /participants/ Таблица видна
Автор отправляет result в форме своего выступления Поле не изменяет результат
GET на адрес удаления своей регистрации Только подтверждение, запись остаётся
POST подтверждения удаления Своя регистрация удаляется
Администратор назначает автомобиль автору без данных владельца Форма с ошибкой; владение не создаётся
Администратор очищает паспорт уже связанного владельца Ошибка; прежние данные сохраняются

Проверка оформления и данных

В Chromium пройдены регистрация, вход, выступление, отзыв, формы результата, Django-admin, формы практик, поиск, страницы и мобильный каталог. Снимки в отчёте получены из работающего приложения. Изменения последней валидации дополнительно проверены через настоящие POST-формы admin в автоматических тестах.

После сохранения перезапуск приложения не очищает данные: они находятся в PostgreSQL. Команда seed_demo не нужна при каждом запуске.

Сборка отчёта

python -m mkdocs build --strict
python -m mkdocs serve --dev-addr 127.0.0.1:8001

Документация открывается на http://127.0.0.1:8001/. Её порт отделён от порта Django. В каталоге site находится только статическая сборка; она исключена из Git ветки с исходниками.

Главная страница сохраняет отчёт ЛР1 по прежнему адресу. Раздел ЛР2 расположен по /lab2/, дополнительные страницы находятся в его навигации. Публикация этой сборки не публикует PostgreSQL, пароли или сам сервер Django.

Сценарий демонстрации

  1. Показать вариант №5, структуру проекта, модели Conference/Registration/Review.
  2. В каталоге продемонстрировать поиск, тематику и переход на вторую страницу.
  3. Создать автора, зарегистрировать тему и аннотацию, изменить их.
  4. Добавить отзыв и показать ограничение рейтинга 1–10.
  5. Войти администратором, показать таблицу участников и фильтр конференции.
  6. Выставить результат в клиентском интерфейсе и открыть ту же запись в Django-admin.
  7. Снова войти автором и показать результат; изменить аннотацию и объяснить сброс решения.
  8. Удалить свою регистрацию через подтверждение.
  9. Показать практики: User, Car, Ownership, DriverLicense, FBV и CBV.
  10. Попытаться назначить автомобиль неполному пользователю, показать ошибку.
  11. Запустить тесты и строгую сборку документации.

Вопросы для объяснения решения

Зачем PostgreSQL, если Django поддерживает разные БД? PostgreSQL прямо указан в задании; на нём проверены миграции и ограничения. SQLite в проекте не используется.

Чем отличаются UserCreationForm и обычное сохранение поля password? Первая применяет проверки и хеширование. Пароль не должен сохраняться обычной строкой.

Почему нельзя доверять полю author из POST? Клиент может изменить запрос. Автор берётся из аутентифицированной сессии request.user.

Почему недостаточно скрыть кнопку администратора? Запрос можно отправить вручную. Проверка is_staff должна выполняться в представлении до изменения БД.

Зачем save(commit=False)? Чтобы проверить форму, затем назначить доверенные серверные поля и только после этого сохранить запись.

Зачем ограничение уникальности, если повтор проверяется во view? Два запроса могут пройти предварительную проверку одновременно. Ограничение защищает запись в БД.

Почему даты отзыва дублируют даты конференции? Это снимок контекста написания отзыва; перенос конференции не должен менять уже сохранённые даты отзыва.

Почему даты владельца необязательны в User, но обязательны в Ownership? Общая модель хранит и авторов конференций без автомобиля. При появлении роли владельца модельная валидация требует полный набор атрибутов.

В чём границы clean? Формы вызывают модельную валидацию, но произвольные QuerySet.update и save сами не обязаны вызывать full_clean. Межтабличные правила и проверка пересечений не являются триггерами БД и не защищают от всех гонок.

Почему Django-admin не заменяет клиентский интерфейс? Условие требует разграничения ролей и административных действий также на обычных страницах сайта.

Ограничения

Приложение учебное и локальное. Django 3.2 выбран по условию, но уже не получает поддержку. Для реальной публичной эксплуатации нужны обновление стека и отдельная настройка сервера. Это не относится к публикации статического MkDocs-отчёта.
